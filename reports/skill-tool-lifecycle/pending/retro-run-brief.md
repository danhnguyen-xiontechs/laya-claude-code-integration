You are one session of several. Each measures one tool (or a small group) the same way. Read this whole file, then `.claude/skills/build-skill-tool-workflow/SKILL.md`, and follow both. Language for chat and files you write for the user: Vietnamese for chat, English for report files (like the existing ones in `reports/skill-tool-lifecycle/`).

## What the user asked
Re-run the workflow for the newest PILOT tools of the Laya/Jev report. The tools are already implemented: skip steps 1-3 (brainstorm, Gate A, design is only a short `design.md`, no implementation). Go to the real test: plain Claude (arm A) against Claude + the tool with **Jev live** (arm B, `OPENROUTER_API_KEY` is set; the repo is public, sending to Jev is allowed), then the report. Cost matters: **case agents run on Haiku 5.5 with effort xhigh** (`model: "haiku"`, `effort: "xhigh"`), forced by the user, whatever `route.mjs` says; the independent reviewer may run on opus.

## Decisions already made by the user (do not ask again)

Write each into `agent-review.json` with resolution `accepted by the user for this run (2026-10-18), not fixed` (keep the finding text) and list them in `evaluation.deviations`. Do not fix the tool. ## Size
4-6 cases, 2 repetitions, A and B of a case in the same message, repetition 2 launched B first. At most **6 case agents in flight at once** (several sessions run in parallel; 20 at once made helpers time out before). Case agents get a real prompt, one fresh work folder per case/arm/repetition, and the same prompt text in both arms except one sentence about the tool.

## Lessons from the first runs (all apply)
1. **Arm A cannot hide the tool.** Subagents see this session's skill list and the repo (3 of 4 arm-A agents called the planner skill on their own in the first run). A's prompt says "No <tool> is available in this task: decide yourself; do not look for or use any skill, script or helper from the repo"; B's prompt says the tool is available and how to run it. After the run check A mechanically:
   `node .claude/skills/build-skill-tool-workflow/scripts/subagent_usage.mjs <subagentsDir> --forbid "<tool-slug>|<tool-script>" <workDir...>`
   A case with `forbiddenCalls > 0` is contaminated: discard it, re-run in a new work folder name (`<case>.A2`, so transcripts cannot be mixed up), keep the discarded one in `evidence/contaminated-run<n>/` outside `runs/`, say so in `deviations`.
2. **Keep the answer key away from both arms.** Strip `expected`/gold blocks from fixtures given to agents; if gold lists live in the repo (eval json, reports, saved reviews), the agents work on a copy with them removed (`git archive HEAD`, delete them). Score with a script, never by the agent's claim.
3. **Neutral wrapper, same command in both arms.** Subagents share this session's hooks, so a hook cannot be on for B only. Give both arms the same helper command (e.g. `node plan.mjs --summary`); in A it prints "tool disabled", in B it runs the tool's real core function and logs each engine decision (Jev calls, latency, fallback) to `_logs/<case>.<arm>.r<n>.jsonl`.
4. **Answers come through the hand-back message**, not a final assistant text: read the `SubagentHandback` tool call in the transcript and save it verbatim to `evidence/answers/<case>.<A|B>.txt` (see `reports/skill-tool-lifecycle/codebase-task-explorer/20261017-cte-agent-01/collect.mjs` on branch `claude/cte-rework` or the copy in `main`).
5. **Tokens**: `subagent_usage.mjs <subagentsDir> <workDir...>`; `<subagentsDir>` is `~/.claude/projects/<project>/<session>/subagents`, one flat folder of `agent-<id>.jsonl` (`<project>` = this session's starting directory with `:` `\` `/` replaced by `-`). No match or two matches = `null`, never a guess.
6. **Save what each arm read**: `evidence/texts/<case>.A.txt` and `<case>.B.txt` for both arms (the first output the agent saw; shorten machine paths). The report links them; one arm missing is a caveat.
7. Tests: `node --test` on Node 24 needs a quoted glob (`node --test "<dir>/*.test.mjs"`). Write `unit-tests.json` from the real output.
8. Real-environment limits: no edits to the shared `.claude/` of the base checkout from a worktree session (a hook blocks it); you only add files under `reports/skill-tool-lifecycle/<tool>/<experiment-id>/` and scratch. Do not run `build_main_report.mjs` (the orchestrator builds the index), do not push. Commit your experiment folder on your branch.
9. Redact: no keys, tokens or the Windows user name in committed evidence (replace the home folder with `<home>`).

## Step 7b: a bad result must be reviewed (required)
After `build_tool_report.mjs`, check `summary.json`. The result is **bad** if B costs more tokens than A (paired, more than the noise between repetitions, or >10% with one repetition) and does not pass more cases, or any case is worse in B, or the engine was called but changed nothing the agent used (or fell back on most calls), or your recommendation is REWORK/DROP/INSUFFICIENT_EVIDENCE. Then do not stop at the verdict. Review the tool against this run's evidence: (1) where B's extra tokens went (turns, tool calls per case, what each arm read); (2) why a case got worse (tool wrong, or agent misread a correct output); (3) what the engine actually decided and whether it changed the rules' result and was right; (4) whether the cases were too easy for any tool to show value; (5) cross-check with the open review findings. Write `improvements.md`: 2-4 sentences of diagnosis with numbers, then at most 5 suggestions ranked by expected effect, each with **change** (file/function), **why**, **expected effect** and **how to verify**; include "drop the engine call / keep rules only" or "drop the tool" when the evidence says so. Put the top suggestion in one sentence at the end of the manifest `headline`. Do not implement the suggestions.
